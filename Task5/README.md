## Задание 5. Проектирование GraphQL API

## Итоговое решение

Схема: [client_info_schema.graphql](client_info_schema.graphql).

## Сущности

Схема построена по тем же данным, что и Swagger-контракт client-info:

- `Client` - карточка клиента (id, name, age), поля `documents` и `relatives` - связи на остальные сущности.
- `Document` - документ клиента (id, type, number, issueDate, expiryDate).
- `Relative` - родственник клиента (id, relationType, name, age).

## Запросы

В схеме один запрос - `client(id: ID!): Client`. Он покрывает все три операции исходного REST API:

- `GET /clients/{id}` соответствует запросу поля `client` без вложенных полей `documents` и `relatives`.
- `GET /clients/{id}/documents` соответствует тому же запросу `client` с выбором поля `documents`.
- `GET /clients/{id}/relatives` соответствует запросу `client` с выбором поля `relatives`.

Отдельных queries для документов и родственников не заводили: в REST это были самостоятельные ресурсы из-за ограничений формата (нельзя было выбрать поля внутри одного ответа), в GraphQL эта же гибкость достигается выбором полей в одном запросе к клиенту.

## Как это решает исходную проблему

Потребитель (веб-приложение или core-app) в одном запросе к `client` перечисляет только нужные поля и связи. Это убирает необходимость в отдельных вызовах на каждый объект данных клиента и одновременно не требует передавать все 500 атрибутов карточки клиента, если нужна лишь часть.
