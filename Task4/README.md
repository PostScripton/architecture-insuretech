## osago-aggregator

Функциональная обязанность сервиса - отправка заявок в страховые компании и опрос решений по ним, оформление ОСАГО как процесс остаётся в core-app.

**Собственное хранилище.** osago-aggregator-db (PostgreSQL) нужен: сервис ведёт заявку на ОСАГО асинхронно - создаёт запрос в каждой страховой компании, затем опрашивает решение, пока не получит ответ или не истекут 60 секунд. Это состояние (id заявки на стороне каждой компании, статус ответа, дедлайн ожидания) должно жить между вызовами и быть доступно любой реплике osago-aggregator, а не только той, что приняла исходный запрос, - поэтому это отдельная БД, а не память процесса.

**API для core-app.** Синхронный REST-эндпоинт "создать заявку на ОСАГО": core-app передаёт данные клиента и автомобиля, osago-aggregator сразу подтверждает приём (обращения к страховым компаниям остаются асинхронной фоновой работой внутри сервиса).

**Передача результатов в core-app.** Использован тот же подход, что и для тарифов в Задании 3: osago-aggregator публикует предложение каждой страховой компании в Event Bus сразу по факту получения ответа, а core-app подписан на эти события. Это и даёт нужный бизнесу эффект - предложения появляются у клиента по мере готовности, а не одним пакетом в конце.

## API веб-приложения и его интеграция с core-app

core-app создаёт заявку на ОСАГО через тот же REST API, что и оформление остальных страховок (см. Задание 3). Для отображения предложений по мере поступления обычный REST не подходит - клиенту нужен push, а не опрос. Добавлен канал Server-Sent Events: core-app при создании заявки открывает клиенту SSE-соединение и отправляет в него каждое предложение сразу после того, как получит соответствующее событие из Event Bus. SSE выбран вместо WebSocket, так как поток данных однонаправленный (сервер -> клиент), а HTTP/SSE проще в эксплуатации и достаточно на нагрузке 2500 одновременных заявок.

## Паттерны отказоустойчивости

**core-app -> osago-aggregator (REST, создание заявки).** Timeout - core-app не должен зависать в ожидании ответа при деградации osago-aggregator; Circuit Breaker - при продолжительной недоступности osago-aggregator core-app быстро отдаёт клиенту ошибку вместо накопления зависших запросов.

**osago-aggregator -> страховые компании (REST, создание заявки и опрос решения).** Применены все четыре паттерна:
- Timeout - у каждого обращения к страховой компании есть ограничение по времени, иначе одна медленная компания истощит пул потоков/соединений сервиса;
- Retry - опрос решения по заявке - это по сути повторяемый вызов до получения ответа или истечения 60-секундного дедлайна;
- Circuit Breaker - изоляция одной деградирующей страховой компании от остальных: недоступность одного партнёра не должна тормозить обработку заявок к другим;
- Rate Limiter - защищает согласованную с каждой страховой компанией пропускную способность от всплеска нагрузки (2500 одновременных заявок способны создать кратно больше вызовов, чем компания готова принять).

## Влияние нескольких реплик сервисов

core-app и osago-aggregator задеплоены в нескольких экземплярах, это учтено в двух местах:

1. Событие с предложением по ОСАГО из Event Bus должна обработать именно та реплика core-app, которая держит SSE-соединение с нужным клиентом. Поэтому каждая реплика core-app подписана на топик в своей собственной consumer-группе (получает все события, а не долю по партициям) и локально фильтрует их по открытым у неё SSE-соединениям.
2. Rate Limiter к страховым компаниям должен быть общим для всех реплик osago-aggregator (например, на Redis), а не локальным в памяти пода - иначе фактическая нагрузка на партнёра растёт пропорционально числу реплик и превышает согласованный лимит.
