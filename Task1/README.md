# Задание 1. Технологическая архитектура (to-be)

<img src="/images/tasks/Task1/insuretech_to-be_architecture.svg" alt="InsureTech технологическая архитектура to-be"/>

## Итоговое решение

Схема в draw.io: [InsureTech_технологическая_архитектура_to-be.drawio.xml](InsureTech_технологическая_архитектура_to-be.drawio.xml).

Приложение разворачивается в 3 зонах доступности региона ru-central1 вместо одной зоны в текущей архитектуре. Это закрывает требования по отказоустойчивости (RTO 45 мин, RPO 15 мин, доступность 99,9%) и по равному времени загрузки страниц для пользователей из разных регионов и часовых поясов РФ.

## Путь клиента

Cloud DNS выполняет гео-роутинг и DNS failover, CDN кэширует статику на edge-серверах - это даёт одинаковое время загрузки страниц независимо от региона пользователя. Regional Application Load Balancer балансирует трафик между тремя зонами и проверяет health check каждого backend'а (GET /healthz, интервал 5 секунд), исключая нездоровые поды и целые зоны из балансировки за секунды.

## Масштабирование

Выбрано горизонтальное масштабирование приложения через Horizontal Pod Autoscaler (по CPU и RPS, 3-15 подов на зону) вместо вертикального - оно покрывает рост нагрузки от регионального расширения бизнеса и не создаёт единую точку отказа.

## Kubernetes

Используется один Managed Kubernetes кластер, растянутый на 3 зоны доступности (control plane развёрнут в 3 зонах, node group - в каждой зоне), а не независимые кластеры по зонам. Обоснование выбора приведено отдельным комментарием на схеме.

## База данных

Managed PostgreSQL: 1 primary и 2 синхронные реплики (Patroni) в разных зонах доступности. Автоматический failover при потере primary укладывается в RTO 45 минут. Синхронная репликация даёт RPO около 0, дополнительно WAL-архивирование и инкрементальный бэкап каждые 15 минут в Object Storage обеспечивают RPO не хуже 15 минут даже при потере всех реплик одновременно.

## Шардирование

Шардирование БД не применяется: объём данных 50 GB укладывается в один инстанс с запасом на вертикальное масштабирование. Горизонтальное масштабирование нагрузки на чтение обеспечивают реплики.

Подробное обоснование по каждому пункту (масштабирование, конфигурация Kubernetes, фейловер-стратегия, конфигурация БД и шардирование) приведено в виде комментариев непосредственно на схеме.
